# Start Big Idea

한 줄짜리 아이디어를 **"팀이 방향을 고를 수 있는 상태"**까지 끌고 가는 스킬.

방향이 확정되면 여기서 끝난다. **PRD는 이 스킬의 산출물이 아니다** — start-prd가 이어받는다.

## 이 스킬이 푸는 문제

아이디어가 흐릿한 단계에서 문서부터 쓰면 셋이 무너진다.

1. **사용자가 말한 첫 문장을 그대로 문제로 받는다.** 그건 대개 해법이지 문제가 아니다. 좁은 출발점에 갇힌 채 아래로 파면 더 나은 방향을 아예 못 본다.
2. **대안을 텍스트로만 비교한다.** 표에 세 줄씩 적힌 A·B·C안은 읽어도 판단이 안 선다. 화면으로 보면 3초 만에 갈린다.
3. **기능을 "섬"으로 본다.** 어디서 들어와서 어디로 나가는지를 안 보고 기능 단위로만 설계하면, 나중에 진입 경로가 없는 기능이 나온다.

그래서 이 스킬은 **확장 → 시각화 → 비교**를 강제한다. 아이디어를 받자마자 하나의 안으로 좁히지 말 것.

## start-prd와의 경계

두 스킬은 이어지는 두 구간이다. **겹치는 일을 두 번 하지 않는다.**

| 구간 | 담당 |
|---|---|
| 아이디어 → 문제 프레임 확장 | **start-big-idea** |
| 흐름 맵 (진입·전후·before/after) | **start-big-idea** |
| 해법 후보 도출 + 시각화 | **start-big-idea** |
| 후보 비교 · 방향 선택 · 버린 안 기록 | **start-big-idea** |
| 깊은 맥락 정렬 (권한 구조·상태·과금·뒤집힌 결정) | start-prd Phase 0 |
| MVP 경계 · 역할 카드 | start-prd Phase 2-4, 2-5 |
| 엣지케이스 심문 | start-prd Phase 3-1 |
| 기능 명세 · BDD · PRD 생성 | start-prd Phase 3 |

**인계 지점**: 이 스킬이 `01_탐색워크시트.md`의 0~7번 섹션을 채우고 멈춘다. start-prd가 8번(MVP 경계)부터 이어받는다. 사용자에게 인계를 제안하되, 강요하지 않는다.

start-prd를 쓸 수 없는 환경이면 이 스킬만으로도 방향 확정까지는 완결된다.

## 언제 쓰고, 언제 안 쓰는가

**쓴다**

- 아이디어는 있는데 **어떤 방식으로 풀지가 안 정해진** 상태일 때
- 방향 후보를 여러 개 놓고 비교해서 하나를 고르고 싶을 때
- 텍스트 설명으로는 판단이 안 서서 **화면으로 보고 정하고 싶을** 때
- 기능이 기존 흐름 어디에 붙는지부터 봐야 할 때

**안 쓴다** — 아래에 해당하면 프로토타입을 만들기 전에 말하고 멈춘다

- 방향이 이미 확정됐다 → **start-prd**로 바로 간다 (문서·명세가 필요한 경우)
- 방향이 확정됐고 문서도 필요 없다 → 바로 구현하는 게 낫다
- 지금 필요한 게 상세 설계·데이터 모델·운영 체계다 → MVP 기획 범위 밖
- 이미 만들어진 화면의 시안을 다듬는 일이다 → 이건 탐색이 아니라 디자인 작업이다

## 질문 방식

**수집형**(이미 답이 있고 서로 독립적인 것)은 한 묶음으로 한 번에 묻는다. 하나씩 물으면 취조가 된다.

**결정형**(앞 결정이 뒤 결정을 바꾸는 것)은 하나씩 묻되 **반드시 추천안과 한 줄 근거**를 붙인다. 추천 없는 질문은 사용자에게 숙제를 떠넘기는 것이다.

**스스로 답할 수 있는 건 묻지 않는다.** 기존 화면·기획 문서·정책·코드에서 확인 가능한 것은 직접 찾고, 사용자에게는 **드러나지 않은 의도와 트레이드오프만** 묻는다.

**UI 표현 방식은 되묻지 않는다.** "이걸 모달로 할까요 페이지로 할까요?" 같은 질문을 던지지 말고, 가장 직관적인 형태를 스스로 골라 그린다. 그렇게 그린 형태가 사용성 측면에서 애매하면 **그 지점만** `[확인 필요]`로 표시한다.

## 진행 구조

| 단계 | 내용 | 진행 방식 |
|---|---|---|
| 0. 맥락 | product-context.md 확인 + 최소 4가지 | 게이트 아님 |
| 1. 프레임 확장 | 문제 재정의 + 흐름 맵 + (요청 시) 벤치마킹 | **게이트** |
| 2. 시각화 | 와이어프레임 수준 대안 3~5개 (HTML 1파일) | 게이트 아님 |
| 3. 비교·선택 | 5기준 비교 + 흐름 배치 확인 + 방향 확정 + 버린 안 | **게이트** |
| 4. 인계 | 워크시트 0~7 생성 + 가정·잔여 정리 | — |

게이트에서는 반드시 멈춘다. **"검토했다"는 명시적 확인**을 받은 뒤에만 다음으로 간다. 침묵이나 다른 질문에 대한 답을 승인으로 해석하지 않는다.

사용자가 "이 정도면 된 것 같다"며 두루뭉술하게 넘어가려 해도 게이트를 생략하지 않는다. 대신 **지금 짚어야 할 확인 포인트만 짧게 재정리**해 제시하고 결정을 요청한다.

## [0] 맥락 — 가볍게

**여기서 깊게 파지 않는다.** 방향 후보를 보는 데는 권한 구조나 과금 정책까지 필요 없다. 그건 방향이 정해진 다음 start-prd Phase 0에서 확정한다. 여기서 무거운 맥락 정렬을 하면 게이트가 멀어지고, 아직 버려질 수도 있는 방향에 시간을 쓰게 된다.

**`product-context.md`가 있으면 먼저 읽는다.** 워크스페이스·레포·노션에 있으면 그걸로 대부분 해결된다. 없으면 이 단계에서 만들지 말 것 — start-prd Phase 0이 만든다.

없는 것만, 한 번에 묶어서 묻는다.

1. 제품 한 줄 설명과 현재 핵심 흐름
2. 대상 사용자
3. 이 아이디어의 출발점 — 어떤 문제·요청·관찰에서 나왔는지
4. 결정적 제약 — 깨면 안 되는 기존 정책, 일정, 기술·조직 한계

**연결된 도구가 있으면 먼저 찾아본다.** Notion·Drive·Slack·GitHub·Figma 커넥터가 있으면 기능명·객체명으로 검색해 관련 문서를 읽는다. 사용자가 링크를 주기를 기다리지 않는다.

3개 이상 답이 오면 진행한다. 완벽한 입력을 기다리며 멈추지 말 것.

## [1] 프레임 확장 + 흐름 맵

### 1-1. 문제를 다시 쓴다

사용자가 말한 **해법**이 아니라 **문제**를 한 문장으로 다시 쓴다. 둘이 어긋나 있으면 그 자리에서 지적한다.

그 다음 **더 넓은 문제 공간으로 한 번 확장한다.** 사용자가 던진 요청을 그대로 출발점으로 삼지 않는다.

```
받은 것: "댓글에 좋아요 버튼 넣어주세요"
좁은 문제: 댓글에 반응할 방법이 없다
넓힌 문제: 어떤 댓글이 쓸모 있었는지 나중에 아무도 알 수 없다
        → 좋아요 / 채택 표시 / 정렬 변경 / 요약 — 해법이 완전히 갈린다
```

프레이밍이 둘 이상 가능하면 **2~3개를 나란히 제시한다.** 프레이밍이 갈리면 해법도 전부 갈리므로 여기서 잡는 게 가장 싸다.

### 1-2. 사용자도 의도를 정리하지 못한 상태라면

질문만 던지지 말 것. 주어진 한 줄에서 읽을 수 있는 단서만으로 **후보 프레임 몇 개를 제시하고** "이 중 어느 쪽에 가까울까요?"로 확인부터 받는다.

단, 이 후보는 추측이지 확정이 아니다. 후보를 고른 뒤에도 1-1의 확장을 다시 시도하고, 여전히 불확실한 부분은 `[확인 필요]`로 남긴다.

### 1-3. 흐름 맵

**기능 단위 섬이 아니라 흐름 단위로 본다.** 이 맵이 [2]의 기준이 되고, 와이어프레임으로 내려갈 때 막막함을 줄인다.

- 진입 경로 — 사용자가 어디서 들어오는가 (메뉴·알림·딥링크·검색·공유)
- 사용자가 왜 이 지점에 왔는가
- 전후 화면 흐름
- before / after — 지금은 어떻게 하고 있고, 이후엔 어떻게 되는가

mermaid로 그린다. 형식과 패턴은 `references/wireframe-guide.md`를 읽을 것.

**[2]의 프로토타입에도 흐름 표시가 있지만 역할이 다르다.** 여기서 그리는 건 **전체 흐름과 모든 진입 경로**(as-is 포함)고, [2]의 것은 **그 안에서 각 안이 붙는 구간만** 잘라 보여주는 것이다. 같은 그림을 두 번 그리지 말 것 — [2]에서 전체 흐름을 다시 그리고 있으면 잘못 가고 있는 것이다.

이미 보이는 화면·기획이 있으면 그걸 기반으로 **비어 있는 부분만** 확인한다.

### 1-4. 벤치마킹 — 사용자가 요청할 때만

**기본은 실행하지 않는다.** 유사 기능이 흔해 보이면 한 줄로 제안하고("비슷한 기능 쓰는 제품 2~3개 훑어볼까요?"), 하자고 할 때만 돌린다.

이 단계가 **문제 정의 다음, 후보 도출 직전**에 있는 이유가 있다. 순서가 앞으로 가면 기능 베끼기가 된다. 남의 제품에서 보이는 건 결과물이고, 안 보이는 건 그들의 제약과 이유다.

- **사례 2~3개까지만.** 기능 매트릭스를 그리지 않는다
- 사례마다 **세 줄만** — 무엇을 어떻게 풀었나 / 그들의 전제가 우리와 같은가 / 가져올 것 하나
- **확인한 것과 추정을 구분한다.** 실제로 본 화면·문서는 그대로, 추측한 의도는 `[추측]`
- 결과는 후보를 만드는 **재료**로만 쓴다. "그래서 우리도 이렇게 한다"로 직행하지 않는다

### 게이트

문제 재정의와 흐름 맵을 보여주고 멈춘다. 확인받을 것은 둘이다 — **문제를 이렇게 보는 게 맞는가**, **흐름 맵에 빠진 경로가 없는가**.

여기가 틀리면 [2]에서 만든 프로토타입이 전부 폐기된다.

## [2] 시각 대안 만들기

### 2-1. 후보를 넓게 편다 — 3~5개

의도적으로 축을 섞는다. 비슷한 안 다섯 개는 하나만 있는 것과 같다.

- **가장 작은 것** — 기존 화면에 필드·버튼 하나 추가 수준
- **정공법** — 제대로 만드는 안
- **운영·수동 우회** — 개발 없이 사람이 처리하는 안 (MVP 정답인 경우가 꽤 있다)
- **기존 자산 재활용** — 이미 있는 기능의 확장

각 안에 붙이는 것:

| 항목 | 내용 |
|---|---|
| 핵심 한 줄 | 이 안이 무엇인가 |
| 크기 | S / M / L |
| **성립 조건(가정)** | 이 안이 성립하려면 참이어야 하는 것 |
| **기술 관점 한 줄** | 무엇에 물려 있고(기존 정책·외부 서비스·데이터·권한) 어디가 위험해 보이는지 |
| 흐름 내 위치 | [1]의 흐름 맵 어디에 붙는가 |
| 판단 포인트 | 이 안을 볼 때 확인할 것 |

기술 관점은 여기서 깊게 파지 않는다. [3] 비교표의 "기술 파급"을 채울 수 있을 정도면 충분하다.

### 2-2. 와이어프레임으로 그린다

**HTML 파일 하나에 모든 안을 담는다.** 파일명은 `00_프로토타입.html`. 템플릿은 `assets/prototype-template.html`을 읽고 구조를 따를 것.

한 파일에 담는 이유는 **비교가 목적**이기 때문이다. 안마다 파일이 나뉘면 창을 오가느라 비교가 안 된다.

지켜야 할 제약 — 자세한 규칙은 `references/wireframe-guide.md`:

- **와이어프레임 수준을 넘지 않는다.** 위치·순서·레이아웃이 보이는 정도. 색·아이콘·브랜딩·실제 카피를 넣지 않는다
- **빠르게 여러 개.** 하나를 완성도 높게 마무리하는 데 시간을 쓰지 않는다
- **목표 기여도가 높은 디테일만.** "있으면 좋고 없어도 그만"인 요소는 과감히 뺀다
- **미확정 영역은 그럴싸하게 채우지 않는다.** `[확인 필요]` placeholder로 명확히 남긴다. 이건 최종 디자인이 아니라 **결정을 돕는 도구**이고, 그 사실이 시각적으로도 유지돼야 한다
- **미확정은 탭 안에만 두지 않는다.** 안마다 흩어져 있으면 탭을 전부 눌러야 전체가 보인다. 템플릿 하단의 "미확정 모아보기"가 각 안의 `[확인 필요]`를 자동으로 긁어 한 목록으로 만든다 — **직접 채우지 말 것.** 손으로 적으면 이중 관리가 되고 곧 어긋난다

너무 추상적이면 판단이 안 되고, 너무 디테일하면 의도하지 않은 내용이나 사용성 왜곡이 생긴다.

## [3] 비교 · 흐름 배치 확인 · 선택

### 3-1. 5기준으로만 비교한다

기준을 늘리면 결론이 흐려진다. **표는 프로토타입 HTML 안에서 한 번만 만든다** — 화면을 보면서 판단하는 자리가 거기이기 때문이다. 워크시트 5번에는 완성된 표를 **그대로 옮기고, 다시 만들지 않는다.**

| 기준 | 보는 것 |
|---|---|
| 고객 적합도 | [1]에서 재정의한 문제를 얼마나 직접 해결하는가 |
| 기존 정책과의 충돌 | [0]에서 확인한 제약을 깨지 않는가 |
| 기술 파급 | 데이터 모델 변경·마이그레이션·기존 API 영향 |
| 개발 비용 | 대략적 크기 |
| 되돌리기 비용 | 틀렸을 때 갈아엎기 쉬운가 |

### 3-2. 흐름 안에 놓아본다

확정 전에 각 안을 **실제 흐름 안에 놓아도 되는지** 확인한다. 이 확인이 없으면 나중에 와이어프레임을 그릴 때 막막해진다.

- 어디서 진입하는가 — **진입 경로가 아예 없는 안**이 여기서 걸린다
- 사용자가 왜 이 지점에 왔는가
- 전후 흐름이 이어지는가
- 눌러보고 이동해 볼 수 있을 만큼 구체적인가
- 지금 보이는 엣지·리스크·정책 충돌 소지

**보이는 엣지·리스크는 승인 전에 보여준다.** 승인 후에 튀어나오는 리스크가 방향을 뒤집는다.

### 3-3. 추천 앞에 "결론을 바꾸는 미지수"를 세운다

추천보다 **먼저** 나와야 하는 게 있다. 지금 모르는 것 중 **알게 되면 선택이 달라지는 것**이다.

이건 특정 안의 판단 포인트가 아니라 **전체 선택의 선행 조건**이다. 예를 들어 "문의가 실제로 몇 건인가"를 모르면 어느 안도 근거 있게 못 고른다. 이런 항목이 특정 안의 판단 포인트 한 줄에 묻히면, 사용자는 그걸 못 본 채로 추천을 승인하게 된다. **그 승인이 나중에 뒤집히는 게 이 스킬이 막으려는 문제다.**

프로토타입 상단의 "결론을 바꾸는 미지수" 블록에 올린다. 각 항목에 **알게 되면 어느 안으로 기우는지**를 한 줄 붙인다 — 그게 없으면 그냥 미결일 뿐 선행 조건이 아니다.

여기가 비어 있지 않은데 추천을 세게 쓰지 않는다.

### 3-4. 하나를 추천한다

"상황에 따라 다릅니다"로 끝내지 말 것. **하나를 고르고 이유를 쓴다.** 근거가 부족하면 "이 판단은 X 가정에 의존합니다"라고 명시한다.

단, 추천은 **참고용 시작점**이지 승인 요구가 아니다. 사용자의 주도적 결정을 유도한다.

[1]에서 재정의한 문제와 고른 해법이 실제로 맞물리는지 여기서 한 번 더 본다. 탐색 도중 문제가 재정의됐는데 해법만 초기 안에 남아 있는 경우가 흔하다.

### 3-5. 버린 안과 버린 이유를 남긴다

**이 스킬에서 빠지기 가장 쉬운 단계다.** 대안을 여러 개 뽑아놓고 탈락 이유를 안 남기면, 나중에 "그건 왜 안 해요?"가 나올 때 재논의가 처음부터 돈다.

각 탈락 안에 **한 줄 이유** + **어떤 조건이 바뀌면 다시 검토할 만한지**를 적는다.

### 게이트

확인받을 것은 셋이다 — **고른 방향이 납득되는가**, **버린 이유가 납득되는가**, **짚어둔 엣지·리스크를 함께 본 상태인가**.

여기서 확정된 방향이 뒤집히면 이후 전부가 폐기된다.

## [4] 인계

### 4-1. 가정과 잔여를 정리한다

끝까지 가도 전부 결정되지는 않는다. 남은 것을 서술로 감추지 말고 모아서 적는다.

- **가정으로 처리한 것** — 가정임을 명시하고 **틀렸을 때 무엇이 무너지는지** 한 줄. 파급을 못 쓰겠으면 그건 가정이 아니라 미결이다
- [1]에서 프레임을 넓히며 세운 가정, 흐름 맵에서 비어 있어 적당히 처리한 부분
- 아직 확인하지 못한 것 / 나중에 확인할 것
- 방향은 확정됐지만 세부가 열려 있는 지점

`[확인 필요]`가 전체 방향을 지배하지 않도록, **확정된 것과 확인 필요한 것을 사용자가 단번에 구분할 수 있게** 남긴다.

### 4-2. 워크시트를 만든다

`01_탐색워크시트.md`의 **0~7번 섹션**을 채운다. 템플릿은 start-prd의 `assets/worksheet-template.md`를 읽고 구조를 그대로 따를 것. 그 파일에 접근할 수 없으면 아래 구조로 쓴다.

```
0. 맥락 정렬        [0]의 결과 + 확인하지 못한 영역
1. 문제 정의        [1-1] 재정의 + 검토한 프레이밍
2. 제약 조건        [0]의 4번
3. 벤치마킹         [1-4] — 실행 안 했으면 "실행 안 함"
4. 해법 후보        [2-1] 표 (성립 조건·기술 관점 포함)
5. 비교             [3-1] 5기준
6. 선택             [3-4] 선택 + 이유 + 의존하는 가정 + [3-3] 결론을 바꾸는 미지수
7. 버린 안과 이유   [3-5]
```

8번(MVP 경계) 이후는 **비워둔다.** start-prd가 채운다.

**파일이 이미 있으면 덮어쓰지 않는다.** 8번 이후가 채워져 있으면 start-prd가 이미 지나간 문서다 — 그 부분은 그대로 두고 0~7번만 갱신하며, 기존 내용과 충돌하면 반영 전에 무엇이 달라지는지 보여주고 판단을 받는다.

### 4-3. 다음 단계를 제안한다

```
방향이 확정됐습니다. 여기서 멈춰도 되고, 팀 리뷰용 PRD가 필요하면
start-prd로 이어서 MVP 경계 → 엣지케이스 → 기능 명세를 채울 수 있습니다.
(start-prd Phase 0에서 권한 구조·상태·과금 맥락을 한 번 더 확인합니다)
```

강요하지 않는다. 산출물 2개(`00_프로토타입.html`, `01_탐색워크시트.md`)를 전달하고 끝낸다.

## 변경 요청을 받았을 때

사용자가 "이렇게 바꿔"라고 명령조로 말해도 **바로 반영하지 않는다.** 즉시 반영은 편하지만, 그 변경이 이미 확정된 방향이나 흐름과 충돌하면 그게 곧 다음 번 갈아엎기가 된다.

**게이트 이전에는 가볍게** — 그 변경이 프레임·후보군·선택 이유에 어떤 영향을 주는지만 함께 보여주고 다시 확인받는다.

**[3] 게이트 이후에는 구조화해서** — 반영 전에 넷을 정리하고 판단을 요청한다.

1. 변경의 진짜 의도
2. 무엇이 깨지는지 — 확정된 방향·흐름 맵·다른 안과 충돌하는가
3. 같은 목적을 다른 방식으로 달성하는 대안 하나 이상
4. 파급 — 진입 경로, 전후 흐름, 기존 정책, 기술 영향 중 영향받는 것

**단, 이의는 한 번만.** 사용자가 근거를 듣고도 원안을 유지하면 반영하고, 그 결정과 이유를 워크시트에 기록한다. 반복해서 되묻는 건 방해다. 충돌도 파급도 없는 단순 변경(문구, 순서)은 그냥 반영한다.

## 원칙

- **짧고 밀도 있게.** 읽는 것 자체가 일이 되면 실패다. 장황한 서술과 수식어를 배제한다
- **결정 포인트를 텍스트 사이에 묻지 않는다.** 판단해야 할 것은 가장 눈에 띄게 분리해 노출한다
- **하나를 완성하지 말고 여러 개를 빠르게.** 이 단계의 목적은 완성도가 아니라 선택지다
- **모르는 것은 묻는다.** 임의로 채우지 않고, 불가피하게 가정했으면 `[확인 필요]`와 파급을 붙인다
- **근거 없는 확정 금지.** 추측은 `[추측]`으로 표시한다
- **동의보다 지적.** 방향이 틀려 보이면 게이트에서 말한다
- **이미 결정된 것을 다시 묻지 않는다** — 대화나 컨텍스트 파일에 있으면 그대로 쓴다
