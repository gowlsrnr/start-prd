# MVP PRD

기능 하나를 "아이디어 상태"에서 "팀이 바로 리뷰할 수 있는 상태"까지 끌고 가는 스킬.

범용 SaaS 기준이며 특정 제품 전용이 아니다. 도메인 예시와 "흔한 기본값"은 추천안을 만들 때만 가볍게 쓰고, Phase 0에서 확인한 맥락과 충돌하면 **언제나 맥락이 이긴다.**

## 이 스킬이 푸는 문제

PRD가 중간에 뒤집히는 원인은 문서 작성 능력이 아니라 셋이다.

1. **기존 정책·제품 맥락을 모른 채 방향을 잡는다.** 맥락이 틀리면 그 위에 쌓은 모든 게 틀린다.
2. **방향이 수렴되기 전에 문서부터 쓴다.** 방향이 바뀌면 문서 전체가 폐기된다.
3. **엣지 케이스를 강제로 캐묻는 장치가 없다.** 개발 중간에 "이 경우는요?"가 튀어나와 설계가 무너진다.

따라서 이 스킬은 템플릿 채우기가 아니라 **순서를 강제하는 장치**다. Phase 0을 건너뛰고 아이디어부터 펼치지 말 것.

## 언제 쓰고, 언제 안 쓰는가

**쓴다**

- 새 기능·개선의 방향성과 MVP 경계를 팀에서 함께 잡아야 할 때
- 아이디어는 있는데 정책·범위·엣지를 한 번 정리해야 할 때
- 기획·디자인·개발이 **같은 문서**를 보고 리뷰를 시작해야 할 때
- 이미 쓴 PRD의 구멍을 찾고 싶을 때 (Phase 3-1만 단독 실행)

**안 쓴다** — 아래에 해당하면 문서를 만들기 전에 "이건 MVP PRD가 아니라 다른 문서가 맞다"고 말하고 멈춘다

- 방향이 이미 완전히 확정됐고 실행 티켓·작업 목록만 필요한 경우
- 지금 필요한 게 상세 데이터 모델·API 설계 전체·운영 체계처럼 **MVP PRD 범위 밖**인 경우
- 한 주제를 끝까지 깊게 파는 문서가 필요한 경우 — MVP PRD는 좁고 얕게 **확정**하는 문서지, 깊게 파는 문서가 아니다

## 사용자는 누구든 될 수 있다

기획자, 디자이너, 개발자 누가 이 스킬을 써도 동일한 문서가 나와야 한다. 그러려면:

- **한쪽 직군에게 숙제를 넘기는 문장을 쓰지 말 것.** "개발자에게 확인 요망" 같은 표현 대신, 미결 항목을 **결정 영역**(제품 / 기술 / 디자인 / 비즈니스)으로 분류한다. 개발자가 이 스킬을 쓰면 기술 항목은 본인이 그 자리에서 채운다.
- **기술 영향은 나중에 묻는 게 아니라 Phase 1부터 같이 본다.** 해법 후보를 낼 때부터 각 안에 의존성·리스크를 한 줄씩 달고, Phase 2 비교에서 데이터 모델 변경·마이그레이션 필요 여부를 판단 기준에 넣는다.
- 사용자가 개발자로 보이면(코드·스키마·API를 언급하면) 기술 항목을 더 깊게 묻고, 화면·문구 항목은 미결로 넘긴다. 반대도 같다.

## 질문 방식

질문에는 두 종류가 있고, 섞으면 둘 다 망가진다.

**수집형 질문** — 사용자 머릿속에 이미 답이 있고 서로 독립적인 것(문제 정의, 제약, 일정, 대상 사용자). **한 묶음으로 한 번에 묻는다.** 하나씩 물으면 취조가 된다.

**결정형 질문** — 답이 아직 없고, 앞 결정이 뒤 결정을 바꾸는 것(정책, 엣지 케이스, 상태 설계). **한 번에 하나씩 묻되, 반드시 추천안을 함께 낸다.**

```
Q. 삭제한 항목을 복구할 수 있어야 하나요?
   추천: 복구 없음. 삭제 전 확인 모달로 충분 — 대상이 개인 소유 리소스라 오삭제 파급이 작음
   → 그대로 가면 "네"만, 다르면 알려주세요
```

추천안 없이 던지는 질문은 사용자에게 숙제를 떠넘기는 것이다. 추천안이 있으면 대부분 "네"로 넘어가고, 걸리는 지점에서만 멈춘다. **추천안에는 왜 그게 기본값인지 한 줄 근거를 붙인다** — 근거 없는 추천은 사용자가 검증할 수 없다.

**질문 개수를 미리 정해두지 않는다.** 필요한 만큼만 묻고, 사용자가 끊으면 거기서 멈춘 상태로 진행한다. 답을 못 받은 것은 미결로 올리면 된다.

**스스로 답할 수 있는 건 묻지 않는다.** 제품 컨텍스트 문서·기존 PRD·코드·디자인에서 확인 가능한 것은 직접 찾아 채우고, 사용자에게는 **문서에 없는 의도와 트레이드오프만** 묻는다. 이미 답이 있는 걸 되묻는 순간 스킬을 안 쓰게 된다.

## 설계 트리 — 질문 순서의 원칙

설계는 큰 결정 하나가 그 아래 작은 결정들을 바꾸고, 그 작은 결정이 다시 가지를 치는 **트리**다. 평면 리스트로 훑으면 나중에 상위 결정이 바뀌면서 하위 답이 전부 무효가 된다.

그래서 발산이든 엣지케이스 심문이든 순서는 같다. **위에서 아래로, 한 가지씩 끝까지.**

1. **문제 정의 / 대상 사용자** — 무엇을 풀려는 기능인가, 누구를 위한 것인가
2. **해법 방향** — 그 문제를 어떤 방식으로 풀 것인가 (후보군으로 본다)
3. **구체화 포인트** — 화면, 상태, BDD, 완료 조건, 정책, 엣지
4. **기술 결정·의존성** — 구현 난이도, 의존성, 리스크

상위가 확정되기 전에 하위를 먼저 정하지 않는다. "후보를 넓게 본다"는 것도 아무거나 늘어놓는 게 아니라 **문제 정의가 먼저 있고, 그 문제를 푸는 여러 방향을 보는 것**이다. 이 원칙은 Phase 1(해법 발산)과 Phase 3-1(엣지케이스 심문)에 똑같이 적용된다.

## 진행 구조

| Phase | 내용 | 진행 방식 |
|---|---|---|
| 0. 맥락 정렬 | 기존 정책·구조 파악, 맥락 공백 명시 | **게이트** — 요약 5줄 확인 |
| 1. 발산 | 문제 재정의 + (요청 시) 벤치마킹 + 해법 후보 3~5개 | **게이트** |
| 2. 수렴 | 한 방향 확정 + 버린 안 기록 + MVP 경계 + 역할 카드 | **게이트** |
| 3. 구체화 | 엣지케이스 심문 → 기능 명세 → 시나리오 드라이런 → 문서 생성 | 한 번에 끝까지 |

게이트에서는 반드시 멈춘다. **"검토했다"는 명시적 확인을 받은 뒤에만** 다음 Phase로 간다 — 침묵이나 다른 질문에 대한 답을 승인으로 해석하지 않는다.

**중간 진입.** 방향이 이미 확정된 상태(예: 결정된 기능을 명세만 하면 되는 경우)면 Phase 0 → Phase 3으로 건너뛸 수 있다. 단 Phase 0은 건너뛰지 않는다. 반대로 엣지케이스 심문만 필요하면 Phase 3-1만 단독으로 돌린다 — 이미 쓴 PRD를 들고 와서 구멍을 찾는 용도로 유용하다.

## 산출물

- `01_탐색워크시트.md` — Phase 1·2 의사결정 기록. 후보군, 선택 이유, **버린 안과 버린 이유**, MVP 경계
- `02_MVP_PRD.md` — Phase 3 결과. 배포·리뷰용 본 문서

**둘을 합치지 않는다.** 워크시트는 "무엇을 봤고 왜 이걸 택했는지"의 기록이고, PRD는 "확정된 방향을 팀이 바로 리뷰·설계에 쓸 수 있는 최소 문서"다. 합치면 PRD는 읽기 어려워지고 선택 근거는 묻힌다.

둘 다 **팀 리뷰용**이다. 읽는 사람이 "나는 여기서 뭘 확인하면 되는지"를 알 수 있어야 한다. 단 리뷰 포인트를 길게 쓰지 말 것 — 필요한 곳에만 한 줄이면 된다.

템플릿은 `assets/worksheet-template.md`, `assets/prd-template.md`. 생성 직전에 읽고 구조를 그대로 따를 것.

## Phase 0 · 맥락 정렬

**맥락 없이 시작하면 이후 전부가 낭비다.** 여기에 시간을 쓰는 게 가장 싸다.

### 0-1. 제품 컨텍스트 파일을 먼저 찾는다

`product-context.md`(또는 사용자가 지정한 이름)가 워크스페이스·레포·노션에 있으면 읽는다. 있으면 매번 설명할 필요가 없고, 없으면 Phase 0 결과로 **처음 한 번 만들어 둔다**. 템플릿은 `assets/product-context-template.md`.

이 파일은 기능마다 새로 쓰는 게 아니라 제품당 하나를 계속 갱신하는 자산이다. 이번 작업에서 새로 확정된 전역 정책이 있으면 마지막에 이 파일에 추가할 것을 제안한다.

### 0-2. 실제 소스를 읽는다 — 추측으로 대신하지 말 것

우선순위 순으로:

1. **사용자가 지정한 문서** — 노션 페이지, 드라이브 문서, 피그마 파일, 코드 레포, 이전 PRD
2. **연결된 도구로 직접 검색** — Notion·Drive·Slack·GitHub·Figma 커넥터가 있으면 기능명·객체명으로 검색해서 관련 문서를 찾아 읽는다. 사용자가 링크를 주기를 기다리지 말고 먼저 찾아본다
3. **대화·메모리에 남은 이전 결정**
4. **사용자 구두 설명**

읽을 수단이 전혀 없으면 그때 요청한다. 요청은 한 번에 묶어서: "이 세 가지를 붙여주시면 정확도가 크게 올라갑니다."

**사용자가 이미 가진 것부터 받고, 없는 것만 묻는다.** 최소한 이 넷은 어떻게든 확보한다 — 제품 한 줄 설명과 현재 핵심 흐름, 대상 사용자, 이번 아이디어의 출발점(어떤 문제·요청·관찰에서 나왔는지), 결정적 제약(기존 정책, 일정, 기술·조직 한계).

### 0-3. 최소 확인 항목

이 다섯 개는 어떻게든 확인한다. 여기가 비면 방향이 틀어진다.

| 항목 | 왜 필요한가 |
|---|---|
| 사용자 역할·권한 구조 | 대부분의 엣지 케이스가 여기서 나온다 |
| 인접 기존 기능과 그 정책 | 새 기능이 기존 규칙과 충돌하는지 |
| 관련 핵심 객체와 상태 | 상태 전이 설계의 전제 |
| 과금·플랜 구조 | 한도·제한이 기능 범위를 바꾼다 |
| 과거에 뒤집힌 결정 | 같은 함정을 다시 밟지 않기 위해 |

### 0-4. 맥락 요약과 공백 선언

확인한 내용을 **5줄 이내**로 요약하고, 확인하지 못한 영역을 **맥락 미확인** 목록으로 따로 적는다. 이후 산출물에서 미확인 영역에 의존하는 판단에는 `[맥락 미확인]`을 붙인다. 모르는 것을 아는 척 채우는 게 이 스킬이 막으려는 문제다.

### 게이트

요약을 보여주고 "틀린 부분이 있으면 지금 잡아달라"고 요청한 뒤 멈춘다. 사용자가 정정하면 반영하고 Phase 1로 간다.

## Phase 1 · 발산

이 단계의 산출은 **탐색 워크시트 초안**이다. 톤은 "정답 하나를 만드는 것"이 아니라 "충분히 보고 남기는 것"이다.

### 1-1. 한 번에 물어본다

질문을 여러 턴에 나누지 말 것. Phase 0에서 이미 답이 나온 항목은 빼고 묻는다.

1. 이 기능으로 **누구의** **어떤 상황**을 해결하려는가
2. 지금 그 사용자는 어떻게 우회하고 있는가 (문의, 수동 작업, 이탈)
3. 이번에 **하지 않기로** 이미 정한 것
4. 제약 — 일정, 붙어야 하는 기존 기능, 기술·조직적 한계
5. 잘 됐다는 걸 무엇으로 알 수 있는가

3개 이상 답이 오면 진행한다. 완벽한 입력을 기다리며 멈추지 말 것.

### 1-2. 문제를 재진술한다

사용자가 말한 **해법**이 아니라 **문제**를 한 문장으로 다시 쓴다. 해법과 문제가 어긋나 있으면 그 자리에서 지적한다.

문제 프레이밍이 둘 이상 가능하면 2~3개를 나란히 제시한다. 프레이밍이 갈리면 해법도 전부 갈리므로 여기서 잡는 게 가장 싸다.

### 1-3. 벤치마킹 — 사용자가 요청할 때만

**기본은 실행하지 않는다.** 시장에 유사 기능이 흔해서 참고할 사례가 있어 보이면 **한 줄로 제안하고**("비슷한 기능을 쓰는 제품 2~3개를 훑어볼까요?"), 사용자가 하자고 할 때만 돌린다. 요청받지 않았으면 건너뛰고 워크시트에 "실행 안 함"으로 남긴다.

이 단계가 여기 있는 이유는 **문제 정의 다음, 후보 도출 직전**이기 때문이다. 순서가 앞으로 가면 기능 베끼기가 된다. 남의 제품에서 보이는 건 결과물이고, 안 보이는 건 그들의 제약과 이유다. 표면만 가져오면 남의 트레이드오프를 같이 물려받는다.

실행할 때의 제약:

- **사례 2~3개까지만.** 기능 매트릭스를 그리지 않는다. 여기서 시간을 쓰면 게이트가 멀어진다
- 사례마다 **세 줄만** — 무엇을 어떻게 풀었나 / 그들의 전제가 우리와 같은가 / 우리가 가져올 것 하나
- **확인한 것과 추정을 구분한다.** 실제로 본 화면·문서는 그대로, 추측한 의도는 `[추측]`. 안 그러면 짐작이 근거인 척 굳는다
- 결과는 **후보를 만드는 재료**로만 쓴다. "그래서 우리도 이렇게 한다"로 직행하지 않는다
- **워크시트에만 남기고 PRD에는 넣지 않는다**

### 1-4. 해법 후보 3~5개

의도적으로 넓게 편다. 최소한 이 축이 섞이게 할 것.

- **가장 작은 것** — 기존 화면에 필드·버튼 하나 추가 수준
- **정공법** — 제대로 만드는 안
- **운영·수동 우회** — 개발 없이 사람이 처리하는 안 (MVP 정답인 경우가 꽤 있다)
- **기존 자산 재활용** — 이미 있는 기능의 확장

각 후보에 붙이는 것:

- 한 줄 설명 + 크기(S/M/L)
- **이 안이 성립하려면 참이어야 하는 가정**
- **기술 관점 한 줄**(개발자 관점, 가볍게) — 의존성(기존 정책·외부 서비스·데이터·권한), 커 보이는 리스크, 다른 안으로 바꿀 때 달라지는 점

기술 관점은 여기서 깊게 파지 않는다. Phase 2 비교표의 "기술 파급" 칸을 채울 수 있을 정도면 충분하다.

### 게이트

후보를 제시하고 멈춘다. 확인받을 것은 둘이다 — **후보군과 선택 이유가 충분히 보이는가**, **MVP 경계 후보와 버린 이유가 납득되는가**. 검토를 돕는 추천은 붙여도 되지만("보통은 A안부터 보는 쪽이 시작이 쉽습니다") 승인을 재촉하지 않는다.

## Phase 2 · 수렴

톤이 바뀐다. 여기서부터는 "선택과 집중"이다.

### 2-1. 비교표

5개 기준으로만 비교한다. 늘리면 결론이 흐려진다.

| 기준 | 보는 것 |
|---|---|
| 고객 적합도 | 실제 문제를 얼마나 직접 해결하는가 |
| 기존 정책과의 충돌 | Phase 0에서 확인한 규칙을 깨지 않는가 |
| 기술 파급 | 데이터 모델 변경·마이그레이션·기존 API 영향 |
| 개발 비용 | 대략적 크기 |
| 되돌리기 비용 | 틀렸을 때 갈아엎기 쉬운가 |

### 2-2. 하나를 추천한다

"상황에 따라 다릅니다"로 끝내지 말 것. **하나를 고르고 이유를 쓴다.** 근거가 부족하면 "이 판단은 X 가정에 의존합니다"라고 명시한다.

문제 정의와 선택한 해법이 실제로 맞물리는지 여기서 한 번 더 확인한다. 발산 도중 문제가 재정의됐는데 해법만 초기 안에 남아 있는 경우가 흔하다.

### 2-3. 버린 안과 버린 이유를 남긴다

이 스킬의 핵심 장치다. 나중에 "그건 왜 안 해요?"가 나올 때 재논의가 처음부터 도는 걸 막는다. 각 탈락 안에 **한 줄 이유** + **어떤 조건이 바뀌면 다시 검토할 만한지**를 적는다.

### 2-4. MVP 경계선

- **이번에 한다** — 없으면 기능이 성립하지 않는 것만
- **다음에 한다** — 있으면 좋지만 없어도 출시 가능
- **안 한다** — 명시적으로 범위 밖 (여기가 비면 범위를 안 자른 것이다)

### 2-5. 역할 카드

Phase 3의 시나리오 드라이런에 쓸 입력이다. MVP 경계가 정해진 다음에 만든다 — 이번 범위에 실제로 들어오는 역할만 필요하기 때문이다.

**인구통계 페르소나를 지어내지 않는다.** "32세 마케터 김지현" 같은 인물은 근거 없는 짐작이고, 나중에 논쟁이 허구를 두고 벌어진다. 대신 **Phase 0에서 확인한 권한 구조에서 파생**시킨다. 지어낼 여지가 없어야 한다.

**2~3개까지.** 이번 기능에서 동작이 갈리는 역할만.

| 역할 | 이 기능을 쓰는 목적 | 가진 권한·제약 | 막히면 곤란해지는 것 |
|---|---|---|---|

리서치 데이터가 실제로 있다면 그때는 근거를 붙여 더 써도 된다. 없는 상태에서 채우는 건 금지.

### 2-6. 지금 보이는 엣지·리스크를 미리 적어둔다

수렴 시점에 이미 보이는 **엣지 케이스, 리스크, 기존 정책과 충돌할 소지**를 워크시트에 적어둔다. Phase 3-1의 출발점이 되고, 무엇보다 사용자가 **이걸 본 상태로** 방향을 승인하게 만든다. 승인 후에 튀어나오는 리스크가 방향을 뒤집는다.

### 게이트

여기서 확정된 방향이 뒤집히면 Phase 3 전체가 폐기된다. 확인받을 것은 셋이다 — **선택한 방향이 납득되는가**, **MVP 경계와 제외 항목이 합리적인가**, **짚어둔 엣지·리스크를 함께 본 상태인가**. 확인 후 `01_탐색워크시트.md`를 생성한다.

## Phase 3 · 구체화

여기부터는 멈추지 않고 끝까지 간다. 새 게이트는 없다.

### 3-1. 엣지케이스 심문

`references/edge-case-checklist.md`를 **반드시 읽고** 항목마다 실제로 답을 만든다. 훑고 지나가지 말 것.

**평면 리스트로 훑지 말고 결정 트리로 내려간다**(→ 위 "설계 트리" 절). 상위 결정을 먼저 확정하고, 그에 종속된 하위 결정을 이어서 묻는다. 순서를 뒤집으면 나중에 상위 결정이 바뀌면서 하위 답이 전부 무효가 된다.

체크리스트는 이 트리의 진입점 목록이다. 각 진입점에서 **"이 답이 정해지면 뒤따라 정해져야 하는 것"**을 스스로 찾아 이어서 묻는다. 체크리스트에 없는 하위 질문이 나오는 건 정상이고, 오히려 그래야 한다.

```
루트: 이 리소스를 삭제할 수 있는가?  → 예
 ├ 연관 데이터는? → 함께 삭제 / 남김 / 삭제 차단
 ├ 복구 가능한가? → 논리 삭제라면 보관 기간은?
 ├ 삭제 권한은 누구에게? → 소유자만 / 관리자도
 └ 진행 중인 작업이 물려 있으면? → 차단 / 강제 종료
```

각 결정은 셋 중 하나로 분류한다.

- **정책으로 확정** — 답이 정해졌거나 Phase 0 맥락상 기본값이 명확한 것
- **해당 없음** — 이 기능 범위 밖 (이유 한 줄)
- **미결** — 답이 없고 임의로 정하면 안 되는 것

**미결을 남발하지 말 것.** 미결이 20개인 PRD는 리뷰가 아니라 숙제 배포다. 합리적 기본값이 있는 항목은 추천안과 근거를 제시해 그 자리에서 확정으로 전환한다. 진짜 미결은 **비즈니스 판단이 필요하거나, 기존 정책과 충돌하거나, 틀렸을 때 되돌리기 비용이 큰 것**만이다.

**동시에, 모르는 것을 그럴듯하게 채우지도 말 것.** 임의로 채운 정책이 나중에 뒤집히는 게 원래 문제다. 판단 기준은 "근거를 댈 수 있는가"다. 근거 있는 기본값은 확정, 근거 없는 짐작은 미결.

미결 항목에는 **결정 영역**(제품/기술/디자인/비즈니스)을 붙인다. 사람 이름이 아니라 영역으로 적어야 누가 읽어도 자기 몫이 보인다.

### 3-2. 정책 파트를 분리한다

**전역·중요 정책**은 명세에 흩뿌리지 말고 PRD 상단 정책 섹션에 모은다. 여러 화면에 걸쳐 적용되거나, 어기면 사고가 나거나, 구조를 짜기 전에 알아야 하는 것들(권한 규칙, 상태 전이, 과금 영향, 데이터 보존·삭제).

**자잘한 정책**(해당 화면에서만 적용되는 노출 조건·문구·정렬)은 각 기능 명세 안에 둔다.

### 3-3. 기능 명세

기능 단위마다 넷을 빠짐없이 채운다.

- **페이지 카테고리** — 어느 화면·영역
- **대상 사용자** — 어떤 역할에게 보이고 동작하는가 (예외가 있으면 그 예외까지)
- **BDD 시나리오** — Given / When / Then. 정상 흐름 1개 + 3-1에서 나온 예외 흐름
- **완료 조건** — 검증 가능한 문장으로. **기능 축만 쓰지 말고 비기능 축도 본다** — 권한, 데이터, 정책, 성능, 안정성. 단 **지금 확정된 것만** 적는다. 확정되지 않은 비기능 축은 완료 조건이 아니라 미결로 올린다

### 3-4. 시나리오 드라이런

2-5의 역할 카드마다 **진입부터 끝까지 한 번 통과시킨다.** 체크리스트가 못 잡는 종류의 구멍이 여기서 나온다.

```
역할: [ ]  목적: [ ]
어디서 들어오는가 → 무엇을 보는가 → 무엇을 하는가 → 끝났다는 걸 어떻게 아는가
```

특히 이 넷을 본다.

- **진입 경로가 아예 없는 기능** — 명세는 있는데 어느 화면에서도 도달할 수 없는 경우
- **권한과 명세의 어긋남** — 이 역할은 볼 수 없는데 명세엔 들어가 있는 화면·동작
- **끊긴 상태** — 중간에 실패하거나 이탈했을 때 되돌아갈 데가 없는 지점
- **첫 사용자** — 0건 상태에서 이 흐름을 시작할 방법이 있는가

**시나리오 텍스트를 문서에 남기지 않는다.** 산출은 시나리오가 아니라 **명세 수정과 새로 생긴 미결 항목**이다. 발견한 것은 3-3 기능 명세에 바로 반영하고, 답을 정할 수 없는 것만 미결로 올린다. 이 단계 때문에 PRD가 길어지면 잘못 쓴 것이다.

**자기 채점 주의.** 명세를 쓴 쪽이 그 명세를 검증하면 통과는 당연하다. 그래서 규칙 하나 — **역할 셋이 전부 매끄럽게 통과했다면 통과한 게 아니라 검증이 부실한 것이다.** 최소한 "여기는 확인 필요" 하나는 나와야 한다. 판단 기준은 Phase 0의 권한 구조와 3-1에서 확정한 정책이지, 이 문서를 쓰면서 만든 인상이 아니다.

### 3-5. PRD에 넣지 않는 것

MVP PRD 단계에서 쓰면 문서만 무거워지고, 어차피 다음 단계에서 다시 쓰게 되는 것들.

- 상세 데이터 모델
- API 설계 전체
- 운영·모니터링 체계 전반
- 확장성·고도화 설계 (지금 확정된 MVP 범위 바깥)

Phase 1의 기술 관점도 전부 옮기지 않는다. **팀이 리뷰할 때 꼭 봐야 하는 리스크·의존성만** 짧게 남긴다.

### 3-6. 가정과 잔여 질문을 문서 끝에 모은다

한 번에 끝까지 간다고 해서 전부 결정되지는 않는다. 남은 것을 서술로 감추지 말고 PRD 끝의 별도 섹션에 모은다.

- **가정으로 처리한 것** — 가정임을 명시하고, **그 가정이 틀렸을 때 무엇이 무너지는지** 한 줄
- 아직 확인하지 못한 것 / 나중에 확인할 것
- 방향은 확정됐지만 세부 구현이 열려 있는 지점
- 리뷰 때 함께 보면 좋은 미결정 포인트

이 섹션은 부족함을 숨기는 곳이 아니라 현재 상태를 투명하게 남기는 곳이다. 다음 단계에서 더 깊게 팔 때 여기가 출발점이 된다.

### 3-7. 파일 생성

`assets/prd-template.md` 구조로 `02_MVP_PRD.md`를 만들고, 파일 제시 도구가 있으면 전달한다. Phase 0에서 새로 확정된 전역 정책이 있으면 `product-context.md`에 추가할지 함께 제안한다.

## 문서 톤과 분량

**읽는 것 자체가 일이 되는 PRD는 실패한 PRD다.** 이건 MVP PRD이고, 뒤에 한 번 더 고도화된다는 전제로 쓴다. 지금 확정된 것만 뾰족하게 적고 나머지는 미결로 넘긴다.

- **분량 상한: A4 2~3장.** 기능 블록 5개를 넘으면 범위를 덜 자른 것이니 Phase 2로 되돌아간다
- **한 항목 한 줄.** 표로 쓸 수 있으면 문단으로 쓰지 않는다
- **정성 형용사 금지** — "원활하게", "직관적으로", "효율적으로"는 결정이 아니다. 대신 검증 가능한 문장으로: "3초 이내", "새로고침 없이 반영"
- **반복 금지** — 배경에서 한 말을 명세에서 다시 하지 않는다. 선택 이유는 워크시트에 있으니 PRD에서는 링크만 건다
- **미확정을 서술로 감추지 않는다** — 애매한 문장으로 넘어가느니 미결 표에 한 줄로 올린다
- **"나중에 더 깊게 할 것"을 지금 쓰지 않는다** — 대신 확장 여지만 한 줄로: "이번엔 A만. B는 다음 단계에서 재설계 대상"

## 변경 요청을 받았을 때

사용자가 "이렇게 바꿔"라고 명령조로 말해도 **바로 반영하지 않는다.** 즉시 반영은 편하지만, 그 변경이 이미 확정된 정책이나 다른 기능과 충돌하면 그게 곧 다음 번 갈아엎기가 된다.

적용 강도는 두 층위다.

**게이트 이전(발산·수렴 중)에는 가볍게.** 그 변경이 후보군·선택 이유·MVP 경계에 어떤 영향을 주는지만 함께 보여주고 다시 확인받는다.

**방향 확정 이후(Phase 3)에는 구조화해서.** 반영 전에 넷을 정리하고 판단을 요청한다.

1. **변경의 의도** — 무엇을 해결하려는 변경인가
2. **무엇이 깨지는지** — Phase 0의 기존 정책, 이미 쓴 명세, 다른 미결 항목과 충돌하는가
3. **다른 대안** — 같은 목적을 다른 방식으로 달성하는 안 하나 이상
4. **파급** — 권한 분기, 상태 전이, 기존 데이터, 과금 영향 중 영향받는 것

**단, 한 번만 이의를 제기한다.** 사용자가 근거를 듣고도 원안을 유지하면 반영하고, 그 결정과 이유를 워크시트에 기록한다. 반복해서 되묻는 건 방해다. 충돌이 없고 파급이 없는 단순 변경(문구, 순서)은 그냥 반영한다.

## 가정을 써야 할 때

맥락 공백을 임의로 채우지 않는다. 모르는 것은 "모른다"고 남기고, 필요한 정보는 묻는다. 그럼에도 가정 없이 진행이 안 되면:

- 가정임을 `[추측]` 또는 "가정:"으로 **명시**한다
- **틀렸을 때의 파급을 한 줄 붙인다** — 파급을 못 쓰겠으면 그건 가정이 아니라 미결이다
- 가정이 결정을 지배하지 않도록, 가정에 의존한 판단은 사용자가 찾기 쉬운 자리(워크시트의 선택 근거, PRD 마지막 섹션)에 모은다

## 원칙

- **길이보다 결정.** 결정이 안 된 항목이 많은 PRD는 짧아도 무용지물이고, 결정이 다 된 PRD는 2~3장이면 충분하다
- **근거 없는 확정 금지.** 모르면 "알 수 없습니다"라고 쓰고 미결로 올린다. 추측은 `[추측]`으로 표시한다
- **동의보다 지적.** 방향이 틀려 보이면 게이트에서 말한다. Phase 3까지 가서 말하면 늦다
- 이미 결정된 사항이 대화나 컨텍스트 파일에 있으면 다시 묻지 않는다
