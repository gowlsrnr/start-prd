# mvp-prd

기능 하나를 "아이디어 상태"에서 "팀이 바로 리뷰할 수 있는 상태"까지 끌고 가는 Claude Code 스킬.

PRD가 중간에 뒤집히는 원인은 문서 작성 능력이 아니라 **순서**다. 맥락을 모른 채 방향을 잡고, 방향이 수렴되기 전에 문서부터 쓰고, 엣지 케이스를 캐묻는 장치가 없어서 개발 중간에 설계가 무너진다. 이 스킬은 템플릿 채우기 도구가 아니라 그 순서를 강제하는 장치다.

범용 SaaS 기준이며 특정 제품 전용이 아니다. 기획자·디자이너·개발자 누가 써도 같은 문서가 나오도록 설계했다.

## 설치

Claude Code 안에서 두 줄이면 끝난다. OS도 경로도 신경 쓸 필요 없다.

```
/plugin marketplace add gowlsrnr/start-prd
/plugin install mvp-prd@start-prd
```

업데이트는 `/plugin marketplace update start-prd`.

### 다른 도구에서 쓰려면

스킬 본문을 그대로 붙여넣으면 된다.

```
https://raw.githubusercontent.com/gowlsrnr/start-prd/main/skills/mvp-prd/SKILL.md
```

### 수동 설치

```bash
git clone https://github.com/gowlsrnr/start-prd.git
cp -r start-prd/skills/mvp-prd ~/.claude/skills/
```

## 사용

`/mvp-prd`로 직접 부르거나, 아래처럼 말하면 자동으로 걸린다.

- "이 기능 어떻게 만들지 정리해줘"
- "요구사항 정리해줘" / "개발 들어가기 전에 정리하자"
- "이미 쓴 PRD에 구멍 없는지 봐줘" (엣지케이스 심문만 단독 실행)

## 진행 구조

게이트에서는 반드시 멈추고, 명시적 확인을 받은 뒤에만 다음으로 간다.

| Phase | 내용 | 진행 방식 |
|---|---|---|
| 0. 맥락 정렬 | 기존 정책·구조 파악, 맥락 공백 명시 | **게이트** |
| 1. 발산 | 문제 재정의 + (요청 시) 벤치마킹 + 해법 후보 3~5개 | **게이트** |
| 2. 수렴 | 한 방향 확정 + 버린 안 기록 + MVP 경계 + 역할 카드 | **게이트** |
| 3. 구체화 | 엣지케이스 심문 → 기능 명세 → 시나리오 드라이런 → 문서 생성 | 한 번에 끝까지 |

방향이 이미 확정됐으면 Phase 0 → 3으로 건너뛸 수 있다. 단 Phase 0은 건너뛰지 않는다.

## 산출물

| 파일 | 용도 |
|---|---|
| `01_탐색워크시트.md` | 후보군, 선택 이유, **버린 안과 버린 이유**, MVP 경계 |
| `02_MVP_PRD.md` | 배포·리뷰용 본 문서 (분량 목표 A4 2~3장) |

둘을 합치지 않는다. 워크시트는 "무엇을 봤고 왜 이걸 택했는지"의 기록이고, PRD는 "확정된 방향을 팀이 바로 리뷰·설계에 쓸 수 있는 최소 문서"다.

## 설계 원칙

- **길이보다 결정.** 결정이 안 된 항목이 많은 PRD는 짧아도 무용지물이다
- **미결을 남발하지 않되, 모르는 걸 그럴듯하게 채우지도 않는다.** 판단 기준은 "근거를 댈 수 있는가"
- **버린 안과 버린 이유를 남긴다.** "그건 왜 안 해요?"가 나올 때 재논의가 처음부터 도는 걸 막는다
- **결정형 질문에는 추천안과 한 줄 근거를 붙인다.** 추천 없는 질문은 사용자에게 숙제를 떠넘기는 것
- **미결 항목은 사람 이름이 아니라 결정 영역**(제품/기술/디자인/비즈니스)으로 분류한다
- **명령 즉시 반영 금지.** 변경 요청은 파급·충돌·대안을 정리한 뒤 판단을 받는다 (단, 이의는 한 번만)

## 파일 구성

```
SKILL.md                              스킬 본문
assets/worksheet-template.md          탐색 워크시트 템플릿
assets/prd-template.md                MVP PRD 템플릿
assets/product-context-template.md    제품 컨텍스트 템플릿 (제품당 하나, 계속 갱신)
references/edge-case-checklist.md     엣지케이스 결정 트리 (범용 SaaS, 12개 진입점)
```

`product-context.md`는 기능마다 새로 쓰는 문서가 아니라 제품당 하나를 계속 갱신하는 자산이다. Phase 0에서 이 파일을 먼저 읽으면 매번 같은 설명을 반복하지 않아도 된다.

## 최근 추가된 것

- 사용·비사용 조건 명시 — 안 맞는 경우엔 문서를 만들기 전에 멈춘다
- 설계 트리를 전역 질문 순서 원칙으로 승격 (문제 → 해법 → 구체화 → 기술)
- 후보별 기술 관점 — 개발자 관점을 Phase 2가 아니라 Phase 1부터
- 요청 시에만 실행하는 벤치마킹 단계 (문제 정의 다음, 후보 도출 직전)
- 역할 카드 + 시나리오 드라이런 — 명세를 역할별로 통과시켜 구멍을 찾는 검증
- 완료 조건의 비기능 축 (권한·데이터·정책·성능·안정성)
- PRD에 넣지 않을 것 목록 — 상세 데이터 모델·API 전체·운영 체계·고도화 설계
- 가정과 잔여 질문 섹션 — 가정에 "틀렸을 때 무너지는 것"을 붙인다
- 변경 요청 대응을 2층위로 분리 (게이트 이전은 가볍게 / 확정 이후는 구조화)
