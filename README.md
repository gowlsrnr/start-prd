# start-prd

아이디어를 **"팀이 바로 리뷰할 수 있는 상태"**까지 끌고 가는 Claude Code 스킬 2개.

기획이 중간에 뒤집히는 원인은 문서 작성 능력이 아니라 **순서**다. 맥락을 모른 채 방향을 잡고, 방향이 수렴되기 전에 문서부터 쓰고, 엣지 케이스를 캐묻는 장치가 없어서 개발 중간에 설계가 무너진다. 이 스킬들은 템플릿 채우기 도구가 아니라 그 순서를 강제하는 장치다.

범용 SaaS 기준이며 특정 제품 전용이 아니다. 기획자·디자이너·개발자 누가 써도 같은 결과가 나오도록 설계했다.

## 두 스킬, 두 구간

```
  흐릿한 아이디어                방향 확정                  리뷰 가능한 PRD
        │                          │                             │
        ├──── start-big-idea ──────┤                             │
        │   확장 → 시각화 → 비교    │                             │
        │                          ├────── start-prd ────────────┤
        │                          │  맥락 → 경계 → 엣지 → 명세   │
```

| | start-big-idea | start-prd |
|---|---|---|
| 언제 | 어떤 방식으로 풀지가 **아직 안 정해졌을 때** | 방향은 정해졌고 **문서가 필요할 때** |
| 하는 일 | 문제 프레임 확장, 흐름 맵, 시각 대안 비교, 방향 확정 | 맥락 정렬, MVP 경계, 엣지케이스 심문, 기능 명세 |
| 산출물 | `00_프로토타입.html` + 워크시트 0~7번 | 워크시트 8~13번 + `02_MVP_PRD.md` |
| 게이트 | 2개 (프레임 / 선택) | 3개 (맥락 / 발산 / 수렴) |

**이어서 쓰면** start-big-idea가 워크시트 0~7번을 채우고, start-prd가 8번부터 이어받는다. 같은 걸 두 번 묻지 않는다.

**각각 단독으로도 완결된다.** 방향이 이미 있으면 start-prd만, PRD가 필요 없으면 start-big-idea만 쓰면 된다.

## 설치

Claude Code 안에서 두 줄이면 끝난다. OS도 경로도 신경 쓸 필요 없다.

```
/plugin marketplace add gowlsrnr/start-prd
/plugin install start-prd@start-prd
```

업데이트는 `/plugin marketplace update start-prd`. 스킬 2개가 함께 설치된다.

### 다른 도구에서 쓰려면

스킬 본문을 그대로 붙여넣으면 된다. 각 SKILL.md는 자립적으로 쓰여 있다.

```
https://raw.githubusercontent.com/gowlsrnr/start-prd/main/skills/start-big-idea/SKILL.md
https://raw.githubusercontent.com/gowlsrnr/start-prd/main/skills/start-prd/SKILL.md
```

### 수동 설치

```bash
git clone https://github.com/gowlsrnr/start-prd.git
cp -r start-prd/skills/* ~/.claude/skills/
```

## 사용

`/start-big-idea`, `/start-prd`로 직접 부르거나, 아래처럼 말하면 자동으로 걸린다.

**start-big-idea**
- "이런 거 만들고 싶은데 어떻게 풀지 모르겠어"
- "방향을 여러 개 보고 싶어" / "화면으로 보고 정하자"
- "이 아이디어 좀 넓혀줘"

**start-prd**
- "이 기능 어떻게 만들지 정리해줘"
- "요구사항 정리해줘" / "개발 들어가기 전에 정리하자"
- "이미 쓴 PRD에 구멍 없는지 봐줘" (엣지케이스 심문만 단독 실행)

## start-big-idea

한 줄짜리 아이디어를 **방향이 확정된 상태**까지 끌고 간다. PRD는 만들지 않는다.

| 단계 | 내용 | 진행 방식 |
|---|---|---|
| 0. 맥락 | product-context.md 확인 + 최소 4가지 | 가볍게 |
| 1. 프레임 확장 | 문제 재정의 + 흐름 맵 + (요청 시) 벤치마킹 | **게이트** |
| 2. 시각화 | 와이어프레임 수준 대안 3~5개 | |
| 3. 비교·선택 | 5기준 비교 + 흐름 배치 확인 + 버린 안 | **게이트** |
| 4. 인계 | 워크시트 0~7 생성 + 가정·잔여 | |

**왜 시각화인가.** 표에 세 줄씩 적힌 A·B·C안은 읽어도 판단이 안 선다. 화면으로 보면 3초 만에 갈린다. 모든 안을 **HTML 파일 하나**에 담아 탭으로 갈아끼우며 비교한다. 외부 의존성이 없어 더블클릭으로 열린다.

**왜 흐름 맵인가.** 기능을 "섬"으로 보면 나중에 진입 경로가 없는 기능이 나온다. 진입 경로·전후 흐름·before/after를 mermaid로 먼저 그린다.

**와이어프레임 수준을 넘지 않는다.** 색·아이콘·실제 카피를 넣지 않고, 미확정 영역은 `[확인 필요]`로 눈에 띄게 남긴다. 얌전한 회색 placeholder는 "다 됐네"로 읽힌다.

## start-prd

확정된 방향을 **팀이 바로 리뷰할 수 있는 최소 문서**로 만든다.

| Phase | 내용 | 진행 방식 |
|---|---|---|
| 0. 맥락 정렬 | 기존 정책·구조 파악, 맥락 공백 명시 | **게이트** |
| 1. 발산 | 문제 재정의 + 해법 후보 3~5개 | **게이트** |
| 2. 수렴 | 한 방향 확정 + 버린 안 + MVP 경계 + 역할 카드 | **게이트** |
| 3. 구체화 | 엣지케이스 심문 → 기능 명세 → 시나리오 드라이런 → 문서 생성 | 한 번에 끝까지 |

게이트에서는 반드시 멈추고, **명시적 확인을 받은 뒤에만** 다음으로 간다.

**중간 진입.** 방향이 이미 확정됐으면 Phase 0 → 3으로 건너뛸 수 있다(Phase 0은 건너뛰지 않는다). start-big-idea를 거쳤으면 Phase 0 → 2-4로 이어진다. 엣지케이스 심문만 필요하면 Phase 3-1만 단독으로 돌린다.

## 산출물

| 파일 | 만드는 스킬 | 용도 |
|---|---|---|
| `00_프로토타입.html` | start-big-idea | 안 3~5개를 한 파일에서 비교 |
| `01_탐색워크시트.md` | 0~7 big-idea / 8~13 start-prd | 후보군, 선택 이유, **버린 안과 버린 이유**, MVP 경계 |
| `02_MVP_PRD.md` | start-prd | 배포·리뷰용 본 문서 (분량 목표 A4 2~3장) |

워크시트와 PRD를 합치지 않는다. 워크시트는 "무엇을 봤고 왜 이걸 택했는지"의 기록이고, PRD는 "확정된 방향을 팀이 바로 리뷰·설계에 쓸 수 있는 최소 문서"다.

`product-context.md`는 기능마다 새로 쓰는 문서가 아니라 **제품당 하나를 계속 갱신하는 자산**이다. 먼저 읽으면 매번 같은 설명을 반복하지 않아도 된다.

## 설계 원칙

두 스킬이 공유한다.

- **길이보다 결정.** 결정이 안 된 항목이 많은 문서는 짧아도 무용지물이다
- **미결을 남발하지 않되, 모르는 걸 그럴듯하게 채우지도 않는다.** 판단 기준은 "근거를 댈 수 있는가"
- **버린 안과 버린 이유를 남긴다.** "그건 왜 안 해요?"가 나올 때 재논의가 처음부터 도는 걸 막는다
- **결정형 질문에는 추천안과 한 줄 근거를 붙인다.** 추천 없는 질문은 사용자에게 숙제를 떠넘기는 것
- **미결 항목은 사람 이름이 아니라 결정 영역**(제품/기술/디자인/비즈니스)으로 분류한다
- **명령 즉시 반영 금지.** 변경 요청은 파급·충돌·대안을 정리한 뒤 판단을 받는다 (단, 이의는 한 번만)
- **UI 표현 방식은 되묻지 않는다.** 가장 직관적인 형태를 골라 그리고, 애매한 지점만 `[확인 필요]`로 표시한다
